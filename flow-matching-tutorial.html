01 — The Hook

A River, Not a Ladder

Picture a river delta from above. Thousands of water droplets begin life scattered randomly across the highlands — chaotic, formless. Call this noise. They all end up flowing through the same delta into the ocean — structured, beautiful. Call this the data.

Each droplet doesn't teleport. It doesn't take huge discrete jumps. It just moves a tiny bit in the direction the landscape pushes it, over and over, until it arrives.

That landscape — the field of arrows telling every droplet at every moment which way to go — is what Flow Matching learns.

Now picture a robot arm. It starts in some neutral pose. You want it to smoothly reach for a coffee mug. The arm shouldn't teleport through space, it shouldn't twitch erratically. It should flow — continuously, predictably — from start to goal.

Same idea. Same math. Same model class.

The big idea

Flow Matching is the framework for learning these flows. This tutorial will walk you through what it is, why it's elegant, and why it's quietly taking over robot policy learning and modern vision-language-action models.

02 — The Core Problem

Why Diffusion Was Awkward

Generative modeling has one job: given samples from some complicated distribution (real images, robot trajectories, sentences), learn to produce more. The hard part is that we usually can't write down the data distribution. We only have samples.

Earlier approaches each had pain points:

G

GANs

A discriminator-generator arms race. Unstable, mode-collapsing, vibes-based to train.

V

VAEs

Tractable inference — but blurry outputs and limited expressiveness.

N

Normalizing Flows

Exact likelihoods — but require invertible architectures with tractable Jacobians. Restrictive.

D

Diffusion Models

Beautiful results — but conceptually heavy. Forward SDE, score function, noise schedule, Tweedie correction, variance bookkeeping, hundreds of sampling steps.

Diffusion works, but the path from "I want to generate data" to "okay so I need a forward SDE, a score function, a noise schedule, a Tweedie correction..." is steep.

The shift

Flow Matching asks: what if we just learn the arrows directly? Instead of an elaborate stochastic process you have to invert, you specify a path from noise to data and learn the velocity field that traces it. Training reduces to a simple regression. Sampling reduces to solving an ODE. That's the whole pitch.

03 — Core Intuition

Vector Fields and Flows

What is a vector field?

A vector field is a function that assigns an arrow (a direction and magnitude) to every point in space. Think of a weather map showing wind: at each location, there's an arrow telling you which way the wind blows and how fast.

If you drop a particle anywhere in that field, the arrow tells it which way to move next. The particle's trajectory is determined entirely by following the arrows.

Click anywhere on the canvas below to drop a particle and watch it flow:

click to add particles

What is a flow?

A flow is what you get when you actually integrate that vector field over time. If you start at point $x_0$ at time $t=0$ and follow the arrows, you trace out a smooth path $x(t)$. After a fixed time (say $t=1$), every starting point has been mapped to some endpoint. That mapping is the flow.

If we set things up so that starting points $x_0$ are samples from noise (e.g., Gaussian) and ending points $x_1$ are samples from data, then the flow is a generator. Sample noise, run the ODE, get data.

The big idea

In one sentence

Flow Matching = supervised learning of a vector field whose flow maps noise to data.

That's it. Everything else is bookkeeping.

The two things we need to figure out are:

  1. What target vector field should the network try to match? (We need ground-truth arrows to regress against.)
  2. How do we get those targets when we only have noise samples and data samples — not the field itself?

The clever trick of Flow Matching is answering #2 without ever computing the true marginal vector field. We'll get there next.

04 — Mathematical Foundations

The Math, Slowly

We'll build this up piece by piece. Each equation gets unpacked before it appears.

4.1 — Prerequisite: What is an ODE?

An ordinary differential equation (ODE) is just a rule that says: "given where you are right now, here's how fast you should move." If you know your current position $x$ and time $t$, the ODE tells you your velocity $\frac{dx}{dt}$. You then take a tiny step in that direction, and repeat. That's all "solving an ODE" means — following a trail of breadcrumbs.

4.2 — Prerequisite: Probability Distributions

A probability distribution tells you how likely different outcomes are. A Gaussian (bell curve) means most values cluster near the center; a ring distribution means values cluster on a circle. When we say $x \sim p$, we mean "$x$ is a random sample drawn from distribution $p$."

4.3 — Probability Paths

We have two distributions:

  • $p_0$ — the source distribution. Usually $\mathcal{N}(0, I)$ (Gaussian noise).
  • $p_1$ — the data distribution. We only have samples from it.

A probability path $p_t$ for $t \in [0, 1]$ is a continuous family of distributions that morphs from $p_0$ to $p_1$. Think of it like a movie: frame 0 is pure Gaussian noise, frame 1 is real data, and the in-between frames are smooth interpolations.

Use the slider below to watch noise morph into data:

interpolation demo
0.00

How we choose this path is a design decision. The simplest and most popular choice is the linear interpolant:

Linear Interpolant
$$x_t = (1 - t)\, x_0 + t\, x_1$$

In words: at time $t$, you're a weighted blend of a noise sample $x_0$ and a data sample $x_1$. At $t=0$ you're pure noise. At $t=1$ you're pure data. In between, a mix. The slider above shows exactly this.

4.4 — Vector Fields and the Continuity Equation

If samples follow a flow, the distribution they live in evolves over time. The math that connects "particles moving" to "distributions changing" is the continuity equation:

$$\frac{\partial p_t}{\partial t} + \nabla \cdot (p_t\, u_t) = 0$$

Don't be intimidated. Here's the plain-English version:

  • $p_t$ is the density of where particles are at time $t$.
  • $u_t(x)$ is the velocity arrow at position $x$, time $t$.
  • The equation just says: density doesn't appear or disappear; it gets pushed around by the velocity field.

It's mass conservation for probability.

The true marginal velocity field $u_t(x)$ is the field that transports $p_0$ to $p_1$ along the path $p_t$. If we could regress directly against $u_t(x)$, we'd be done. But we can't compute it — it depends on the whole distribution.

4.5 — The Conditional Trick (this is the magic)

Here's the move that makes Flow Matching tractable.

Instead of trying to learn the marginal velocity (which integrates over all data points), we define a conditional velocity — one that depends on a specific data point $x_1$.

For our linear interpolant $x_t = (1-t)x_0 + t x_1$, what's the velocity? Just take the derivative with respect to $t$:

$$\frac{d x_t}{dt} = -x_0 + x_1 = x_1 - x_0$$
The key insight

The velocity along the straight line from $x_0$ to $x_1$ is just the displacement $x_1 - x_0$. Constant in time, trivial to compute. No noise schedules, no score functions. Just a subtraction.

4.6 — The Conditional Flow Matching Loss

Here's the punchline. The Conditional Flow Matching (CFM) objective is just a regression loss:

CFM Loss (the entire training objective)
$$\mathcal{L}_{\text{CFM}}(\theta) = \mathbb{E}_{t,\, x_0,\, x_1} \left[ \left\| v_\theta(x_t,\, t) - \underbrace{(x_1 - x_0)}_{\text{target velocity}} \right\|^2 \right]$$

Where each term is:

  • $t \sim \mathcal{U}(0,1)$ — sample a random time
  • $x_0 \sim \mathcal{N}(0,I)$ — sample noise
  • $x_1 \sim p_{\text{data}}$ — sample a real data point
  • $x_t = (1-t)x_0 + t x_1$ — build the interpolant
  • $v_\theta$ — your neural network (the learned velocity)

The deep result (Lipman et al., 2023): minimizing this conditional loss is equivalent (up to a constant) to matching the true marginal velocity field. You learn the right thing by regressing on easy targets.

That's the entire training procedure. Three lines:

sample (x0, x1, t)
xt = (1 - t) * x0 + t * x1
loss = || model(xt, t) - (x1 - x0) ||^2

No noise schedules. No score functions. No SDE discretization. No variance bookkeeping. Just regress velocities.

4.7 — Sampling: Integrate the ODE

Once trained, generation is solving an ordinary differential equation:

$$\frac{dx}{dt} = v_\theta(x, t), \quad x(0) \sim \mathcal{N}(0, I)$$

Integrate from $t = 0$ to $t = 1$, and $x(1)$ is your sample. The simplest integrator (Euler) is one line per step:

$$x_{t+\Delta t} = x_t + v_\theta(x_t,\, t)\, \Delta t$$

Walk along the arrows. Want better quality? Use a fancier ODE solver (Heun, RK4, adaptive). Want fewer steps? You can often get away with 5–20 for high-quality samples, compared to diffusion's typical 50–1000.

05 — Pause and Think

Interactive Checkpoint #1

Q1

Why does the network need time $t$?

In Flow Matching with the linear interpolant, the target velocity is $x_1 - x_0$. This is constant in time for a given pair. But the network's prediction $v_\theta(x_t, t)$ takes $t$ as input. Why does the network still need to depend on $t$?

Because the network doesn't see $(x_0, x_1)$ directly — it only sees $x_t$. The same point $x_t$ could lie on many different lines (many different $(x_0, x_1)$ pairs). At early $t$, an $x_t$ that looks noisy probably came from many possible $x_1$'s; at late $t$, the point is close to a specific data point and the inferred velocity is much more certain.

The marginal velocity (what the network actually learns) does change with time — it's the conditional velocity that happens to be constant. The network is averaging over all possible endpoint pairs consistent with the current state, and that average changes with $t$.

Q2

What happens with 1 Euler step?

Suppose you trained a Flow Matching model and at inference you used 1 Euler step (i.e., set $\Delta t = 1$ and take a single jump from $x_0$). What do you predict happens? Will it produce a reasonable sample?

Surprisingly, you'd get something — and for simple distributions, often something half-decent. A single Euler step is $x_1 \approx x_0 + v_\theta(x_0, 0) \cdot 1$. The model's prediction at $t=0$ is roughly $\mathbb{E}[x_1 - x_0 \mid x_0]$, which equals $\mathbb{E}[x_1 \mid x_0] - x_0$.

So the one-step prediction lands at the conditional mean of the data given the noise sample — basically a mode-averaged guess. Multi-step integration follows the curving trajectory in distribution space and resolves to a specific sample rather than the mean. This is exactly the intuition behind one-step distillation methods.

06 — Head to Head

Flow Matching vs Diffusion

Both diffusion and Flow Matching are continuous-time generative models. They are deeply related — under specific path choices, you can show they are mathematically equivalent. But the framings differ in important practical ways.

Takeaway

Flow Matching is a strictly simpler conceptual framework that often runs faster at inference and is easier to tune. Modern "rectified flow" image models like Stable Diffusion 3 are Flow Matching under the hood.

07 — Robotics

Flow Matching in Robotics

The robot policy problem

You want a robot to do things. The classical formulation: given an observation $o_t$ (camera image, joint angles, gripper state), output an action $a_t$ (joint velocities, end-effector pose).

But pointwise action prediction has problems:

  • Multimodality: there are often many valid actions. Predicting their mean produces incoherent in-between motion (the average of "go left" and "go right" is "don't move").
  • Compounding error: small per-step errors accumulate. After 100 steps you've drifted.
  • Jerkiness: independent predictions per step don't enforce smoothness.

The fix: predict an action chunk — a short sequence of future actions (e.g., the next 16) as a single object. The generative model job becomes:

$$\text{model}: o_t \rightarrow p(a_{t:t+H} \mid o_t)$$

Generate a distribution over short trajectories conditioned on what the robot currently sees.

Why Flow Matching fits perfectly

Three reasons it dominates

1. Trajectories are inherently continuous. The velocity-field framing maps directly onto motion.

2. Inference latency matters. At 10–30 Hz control rates, Flow Matching's 5–10 step sampling is a huge advantage.

3. Multimodality is preserved. Like diffusion, it can represent multimodal action distributions without averaging modes.

Architecture of a Flow Matching policy

Worked example — a reaching task

Suppose you have a 7-DoF robot arm and you want it to reach for a cup. Your training data is human demonstrations: image + joint states + future action chunks of length 16.

Training:

  1. Sample a demonstration. Extract the observation $o$ and the ground-truth action chunk $a_1 \in \mathbb{R}^{16 \times 7}$.
  2. Sample $a_0 \sim \mathcal{N}(0, I)$ of the same shape and $t \sim \mathcal{U}(0,1)$.
  3. Form $a_t = (1-t)a_0 + t a_1$.
  4. Predict velocity $v_\theta(a_t, t, \text{encoder}(o))$.
  5. Minimize $\|v_\theta - (a_1 - a_0)\|^2$.

Inference (every ~100ms):

  1. Take current observation $o$.
  2. Start from $a_0 \sim \mathcal{N}(0, I)$.
  3. Run 5–10 Euler steps along $v_\theta$ to get an action chunk.
  4. Execute the first few actions on the robot.
  5. Re-plan from new observation.

This is the recipe behind systems like Physical Intelligence's pi-zero and pi-zero.5 models, and a growing list of academic policies.

08 — Pause and Think

Interactive Checkpoint #2

Q3

Diffusion policy vs Flow Matching policy trajectories

A diffusion policy and a Flow Matching policy are both trained on the same robot demonstrations. The Flow Matching policy needs only 8 ODE steps; the diffusion policy needs 50. Beyond the obvious latency win, what other qualitative differences might you expect in the generated trajectories, and why?

1. Straighter, smoother trajectories. With the linear interpolant, the training targets are straight lines. The learned marginal flow tends to be closer to straight than diffusion's curved schedule.

2. Less mode-mixing under aggressive step reduction. Diffusion's curvier trajectory means reducing step count hurts mode coherence — you can get blends between modes. Flow Matching degrades more gracefully.

3. More predictable timing. Flow Matching trajectories at a given $t$ are at a known fraction of the path from noise to data, making step budgets easier to reason about.

4. Lower variance in jerk/acceleration. The smoother integration tends to produce action chunks with smaller second derivatives, which feels much better on real hardware.

Q4

Why start from Gaussian noise?

Why is starting from Gaussian noise — random arm waving — even a reasonable initialization for a robot policy? Shouldn't we start from the current pose?

The Gaussian is in action space, not joint space — it's noise over what the robot will do, not over where it currently is. The current state is provided as conditioning $c$. The model learns to transform Gaussian noise into an action chunk that is appropriate for $c$.

The randomness gives us a way to sample diverse plausible behaviors when the task is multimodal, while the conditioning anchors everything to the actual scene. It's the same logic as text-to-image diffusion starting from noise but conditioning on a prompt.

09 — Vision-Language-Action

Flow Matching in VLA Models

A Vision-Language-Action (VLA) model is a robot policy with three input modalities: pixels, natural language instruction, and robot proprioception. The output is an action chunk. Leading examples — RT-2, OpenVLA, pi-zero / pi-zero.5 — combine a large pretrained vision-language model (VLM) backbone with an action head.

The action head is where the magic happens. Earlier VLA work used token regression or autoregressive action tokens. The current generation overwhelmingly uses diffusion or Flow Matching action heads, with Flow Matching pulling ahead due to its speed and smoothness.

Full VLA architecture with a Flow Matching head

What each block does

  • Vision encoder: turns images into a sequence of visual tokens. Often a frozen ViT or SigLIP from a pretrained VLM.
  • Language encoder: turns the instruction into text tokens. Often a frozen LLM.
  • VLM backbone: jointly attends over visual and text tokens. This is where pretrained knowledge (open-world semantics, commonsense, object permanence) lives.
  • Flow Matching head: a smaller transformer that takes the current noisy action chunk $a_t$, the time embedding for $t$, and the conditioning context $c$, and predicts the velocity. This is the only part typically trained on robot data; the rest can be frozen or LoRA-tuned.
  • ODE sampler: integrates the predicted velocity field. The standard choice is around 10 Euler steps.

Why Flow Matching is winning in VLAs

  • Latency. Going from 50-step diffusion to 10-step flow matching is a 5x speedup on the action head.
  • Smoother actions. Real hardware vibrates and overshoots when fed jerky commands.
  • Simpler training. Plain MSE means fewer knobs. Every saved hyperparameter sweep is real money.
  • Compatible with everything. Classifier-free guidance, conditioning dropout, action-chunk masking — pretty much every diffusion trick transfers directly.
10 — Working Code

Code Examples

Minimal Flow Matching in PyTorch — 2D Ring

This is a complete, runnable Flow Matching implementation that learns to generate 2D data (a ring of points). Drop it into a .py file and run it.

import torch
import torch.nn as nn
import math

# -------------------------------------------------------------
# 1. The velocity field network v_theta(x, t)
# -------------------------------------------------------------
class VelocityField(nn.Module):
    """A small MLP that takes (x, t) and outputs a velocity vector."""

    def __init__(self, data_dim: int = 2, hidden: int = 128):
        super().__init__()
        # Sinusoidal-ish time features make the network sensitive to t.
        self.time_proj = nn.Linear(1, hidden)
        self.net = nn.Sequential(
            nn.Linear(data_dim + hidden, hidden),
            nn.SiLU(),
            nn.Linear(hidden, hidden),
            nn.SiLU(),
            nn.Linear(hidden, hidden),
            nn.SiLU(),
            nn.Linear(hidden, data_dim),
        )

    def forward(self, x: torch.Tensor, t: torch.Tensor) -> torch.Tensor:
        # x: (B, data_dim)
        # t: (B, 1) with values in [0, 1]
        t_feat = torch.sin(self.time_proj(t))   # cheap nonlinear t embedding
        return self.net(torch.cat([x, t_feat], dim=-1))


# -------------------------------------------------------------
# 2. Toy data distribution — a noisy ring in 2D
# -------------------------------------------------------------
def sample_ring(batch_size: int, radius: float = 2.0,
                noise: float = 0.05) -> torch.Tensor:
    theta = torch.rand(batch_size) * 2 * math.pi
    x = radius * torch.cos(theta) + noise * torch.randn(batch_size)
    y = radius * torch.sin(theta) + noise * torch.randn(batch_size)
    return torch.stack([x, y], dim=-1)


# -------------------------------------------------------------
# 3. Training loop — the entire Flow Matching algorithm
# -------------------------------------------------------------
def train(steps: int = 5000, batch_size: int = 512, lr: float = 1e-3):
    model = VelocityField()
    opt = torch.optim.Adam(model.parameters(), lr=lr)

    for step in range(steps):
        # (a) Sample a batch of real data (x1) and Gaussian noise (x0).
        x1 = sample_ring(batch_size)                       # target samples
        x0 = torch.randn_like(x1)                          # noise samples

        # (b) Sample a random time t per example, in [0, 1].
        t = torch.rand(batch_size, 1)

        # (c) Form the linear interpolant x_t = (1-t) x_0 + t x_1.
        xt = (1.0 - t) * x0 + t * x1

        # (d) The target velocity is the constant displacement x_1 - x_0.
        target_v = x1 - x0

        # (e) Predict velocity, compute MSE loss, backprop. That's it.
        pred_v = model(xt, t)
        loss = ((pred_v - target_v) ** 2).mean()

        opt.zero_grad()
        loss.backward()
        opt.step()

        if step % 500 == 0:
            print(f"step {step:5d} | loss {loss.item():.4f}")

    return model


# -------------------------------------------------------------
# 4. Sampling — solve dx/dt = v_theta(x, t) with Euler steps
# -------------------------------------------------------------
@torch.no_grad()
def sample(model: VelocityField, n: int = 1024,
           n_steps: int = 50) -> torch.Tensor:
    x = torch.randn(n, 2)                # start from pure noise (p_0)
    dt = 1.0 / n_steps
    for i in range(n_steps):
        t = torch.full((n, 1), i * dt)   # current time, broadcasted
        v = model(x, t)
        x = x + v * dt                   # Euler update
    return x                             # x is now (approximately) ~ p_1


# -------------------------------------------------------------
# 5. Run it
# -------------------------------------------------------------
if __name__ == "__main__":
    model = train()
    samples = sample(model)
    print("Sampled mean radius:",
          samples.norm(dim=-1).mean().item(),
          "(target ~2.0)")
What you should observe

The loss drops smoothly, and the final samples cluster around radius 2.0 — the model has learned the ring distribution. The remarkable thing is what's not there: no noise schedule, no $\beta$ values, no variance lower bound, no Tweedie correction. Just three lines of training logic.

VLA Integration Snippet

Here's how a Flow Matching action head slots into a VLA architecture. This is the structural recipe; in practice you'd use a much larger transformer for the velocity head and a real VLM backbone.

import torch
import torch.nn as nn


# -------------------------------------------------------------
# A toy VLM-style encoder (replace with frozen SigLIP + T5)
# -------------------------------------------------------------
class VLMBackbone(nn.Module):
    def __init__(self, embed_dim: int = 512):
        super().__init__()
        self.vision = nn.Linear(3 * 224 * 224, embed_dim)
        self.text   = nn.Embedding(32000, embed_dim)
        self.fuse   = nn.TransformerEncoder(
            nn.TransformerEncoderLayer(
                embed_dim, nhead=8, batch_first=True),
            num_layers=2,
        )

    def forward(self, image, text_ids):
        B = image.shape[0]
        vis_tok = self.vision(image.flatten(1)).unsqueeze(1)
        txt_tok = self.text(text_ids)
        tokens  = torch.cat([vis_tok, txt_tok], dim=1)
        return self.fuse(tokens)  # context c


# -------------------------------------------------------------
# Flow Matching action head — predicts velocity over a chunk
# -------------------------------------------------------------
class FlowMatchingActionHead(nn.Module):
    def __init__(self, action_dim=7, horizon=16,
                 embed_dim=512, hidden=512):
        super().__init__()
        self.action_dim = action_dim
        self.horizon    = horizon
        self.action_in  = nn.Linear(action_dim, hidden)
        self.time_in    = nn.Sequential(
            nn.Linear(1, hidden), nn.SiLU())
        self.cond_proj  = nn.Linear(embed_dim, hidden)

        decoder_layer = nn.TransformerDecoderLayer(
            hidden, nhead=8, batch_first=True)
        self.decoder = nn.TransformerDecoder(
            decoder_layer, num_layers=4)
        self.out = nn.Linear(hidden, action_dim)

    def forward(self, a_t, t, c):
        # a_t: (B, H, A)  noisy action chunk
        # t:   (B, 1)     time in [0, 1]
        # c:   (B, T, d)  fused VLM context
        tok = self.action_in(a_t)        # (B, H, hidden)
        t_emb = self.time_in(t).unsqueeze(1)
        tok = tok + t_emb               # FiLM-style add
        mem = self.cond_proj(c)
        h = self.decoder(tok, mem)       # cross-attend
        return self.out(h)               # (B, H, A) velocity


# -------------------------------------------------------------
# Full VLA policy: backbone + flow head + integrator
# -------------------------------------------------------------
class FlowMatchingVLA(nn.Module):
    def __init__(self, action_dim=7, horizon=16):
        super().__init__()
        self.backbone = VLMBackbone()
        self.head = FlowMatchingActionHead(
            action_dim=action_dim, horizon=horizon)
        self.action_dim = action_dim
        self.horizon = horizon

    # --- training: flow matching loss conditioned on (image, text)
    def loss(self, image, text_ids, a1):
        B = a1.shape[0]
        a0 = torch.randn_like(a1)
        t  = torch.rand(B, 1, device=a1.device)
        at = (1 - t.view(B,1,1)) * a0 + t.view(B,1,1) * a1
        target = a1 - a0
        c = self.backbone(image, text_ids)
        pred = self.head(at, t, c)
        return ((pred - target) ** 2).mean()

    # --- inference: solve the ODE
    @torch.no_grad()
    def act(self, image, text_ids, n_steps=10):
        B = image.shape[0]
        c = self.backbone(image, text_ids)
        a = torch.randn(B, self.horizon, self.action_dim,
                        device=image.device)
        dt = 1.0 / n_steps
        for i in range(n_steps):
            t = torch.full((B, 1), i * dt, device=image.device)
            v = self.head(a, t, c)
            a = a + v * dt
        return a  # (B, H, A) — execute first few, then re-plan
Swapping diffusion for flow matching

To convert a diffusion-policy VLA into a Flow Matching VLA, you only need to: (1) swap the loss from noise-prediction MSE to velocity MSE, and (2) swap the sampler from a noise scheduler to an ODE integrator. Everything else — encoders, backbone, conditioning, action chunking — stays the same.

11 — Summary

Key Insights

Flow Matching in one breath: instead of inverting a noise process, learn the velocity field that morphs noise into data along a straight line, by regressing on the simple displacement $x_1 - x_0$.

1

The path is a design choice

Linear interpolants are simple and work well, but you can choose other paths (variance-preserving, optimal transport). Flow Matching is a framework, not a single algorithm.

2

The conditional trick is the core

Regressing against the constant per-pair displacement is equivalent to regressing against the intractable true marginal velocity. This is the theoretical magic.

3

Sampling is just solving an ODE

This gives you all the tools of numerical ODE solvers: adaptive step sizes, error estimates, parallel-in-time methods.

4

Robotics wins are real

Smoother on hardware, lower latency, easier to tune. Modern VLAs are converging on Flow Matching as the default action head.

When to use Flow Matching

Reach for Flow Matching when...

  • Generating continuous-valued outputs (trajectories, images, audio, latents)
  • You care about sampling latency
  • You want minimal hyperparameter tuning
  • You want smoothness in the output
  • You're building a robot policy or VLA — it's the default

Pick something else when...

  • Pure discrete data (tokens) — autoregressive or discrete diffusion are more natural
  • You need strict likelihood evaluation — some classical normalizing flows have advantages
  • Tiny datasets where simpler models suffice (a Gaussian mixture may be all you need)
If you only remember one thing

Flow Matching is regression on velocities, and that simplicity is its superpower.
